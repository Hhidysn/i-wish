# Full

- 工作顺序：先覆盖整体结果，再按需展开模块细节；使用现有项目记录，无需新增编排运行时。
- 共同约束：沿用入口的 Gate 1 / Gate 2、停等确认与联网调研；职责见 [agents.md](agents.md)，证据见 [verification.md](verification.md)。

# 全局设计

- 能力映射：首个增量前覆盖全部结果与质量目标，将功能、领域方法、工具用法和评价能力关联到负责人、输入、输出、依赖、验收 ID 和证据状态。
- 共享契约：明确接口与 schema 版本、数据与权限归属、兼容性；覆盖信任、权限、隐私、生命周期、失败、恢复与迁移。
- 执行约束：明确顺序、并发、取消、重试、资源限制与可测试入口；可替换内部细节按需展开。
- 场景推演：用代表性的跨模块成功与失败场景检查契约。
- 未知事项：逐项记录问题、负责人、决定性检查、通过目标、备选方案、截止时间和受阻工作。
- 采纳阻塞：身份、许可、必要平台或信任支持不明时，阻塞依赖设计与采纳；指定负责人或日期不能替代答案。
- 性能假设：仅在已授权且有备选方案的实验中验证。
- 开放创意：由不同模型隔离提案，再聚焦比较；真实研究维度交给有界只读研究者，可并行，主代理亲查决定性一手来源。
- 独立审查：冻结全局推荐，使用去偏输入做独立对抗审查；依赖批准或开工前关闭该工作所需的阻塞项。验证采纳未知项的实验按实验设计审查，不要求先得到待验证答案。
- 审查标识：记录设计版本、具名契约、假设、已审决策与未解决发现。
- 方案批准：展示体验、架构、替代方案、复用或自建、义务、未知项、首个集成验证、路线图、委派的模块细节、任务纲要与阶段验收目标。

# 任务与依赖

- 任务类型：纳入决策、调研、设计、实现、集成与验证；已批准计划包含依赖图和阶段验收目标，只细化近期工作。
- 任务粒度：一项任务适合一个新上下文，证明一个可观察结果；优先完整纵向路径，共享基础与分阶段兼容迁移可作前置条件。
- 切片结果：说明交付的端到端行为或产物，不能只描述某一层动作。
- 状态流转：`open → ready → running → verifying → done`；阻塞项单独记录。

| 任务字段 | 内容 |
| --- | --- |
| 目标 | ID、类型、结果、验收 ID、非目标 |
| 归属 | 负责人、允许文件与影响、契约负责人及版本 |
| 输入 | 最小上下文、依赖、交付物、可行检查 |
| 验证 | 独立角色、通过标准、阻塞未知项、恢复与失效条件 |
| 进度 | 状态、证据、下一步 |

| 类型 | 就绪条件 |
| --- | --- |
| 调研 / 决策 | 问题、授权、来源访问、依赖和输出标准齐备；答案可以未知 |
| 设计 | 必要调研支持采纳，相关用户承诺已确定，输出与审查标准齐备 |
| 实现 | 范围已授权，设计与审查有效，输入和契约可用，检查可行，阻塞未知项已关闭 |
| 集成 | 参与方、构建与契约版本可用，集成检查和隔离方式明确 |
| 验证 | 候选版本、标准、独立评估者、工具及可运行输入齐备 |

- 实验就绪：有界实验归入实现或验证任务，按 [research.md](research.md#实验与采纳) 已批准的实验设计、边界、标准和分支判断就绪；被检验答案可未知，结论的消费者仍阻塞，不新增任务类型。
- 精确依赖：指明所需输出，不笼统要求前项全部完成；消费者可基于已批准的版本化契约与可执行 stub 或生产者构建开工，验收仍需真实生产者。
- 循环依赖：将循环集成依赖合为一个集成任务，不伪造 DAG。
- 并行边界：每个文件和共享契约只设一个写入方；语义独立才可并行，路径不同不足以证明，优先调度当前就绪任务。

# 阶段验收

- 开工前定义：明确可用结果、验收与契约覆盖、集成路径、失败与恢复、适用的非功能目标。
- 执行条件：记录环境、独立检查、通过标准、阻塞项及恢复限制。
- 计划审查：独立检查覆盖和依赖风险；已就绪时合并设计审查，否则做一次有界计划检查，不新增固定人工批准。
- 完成依据：验收集成结果，不以任务数量代替结果。

# 模块就绪

首次实现模块，或证据、设计失效时执行：

1. 差异检查：比较结果、约束、验收与共享契约；按 [interview.md](interview.md) 只补问缺失或变化的用户承诺，沿用其余批准。
2. 证据更新：检查既有证据，由有界研究者补查缺失或过时的决定性事实，不重复有效搜索。
3. 细节展开：明确归属、API、数据、状态、不变量、依赖、错误与恢复、资源限制、测试入口和集成；非代码愿望对应产物或计划的相关部分，生产者与消费者一起更新。
4. 独立审查：质询未覆盖决策与失效假设；仅当版本、契约、假设和范围仍适用时复用旧审查。
5. 就绪放行：更新版本、任务就绪状态、验收映射及阶段影响；在授权内推进，只确认变化的已批准承诺。

- 普通任务：引用有效模块设计，不重启采访。
- 契约变化：受影响任务和证据失效，待输入与检查更新后恢复；保留无关任务和结论。

# 局部重规划

- 检查时机：高影响或返工昂贵的决策前，以及复杂问题、反复失败或证据失效时，检查是否缺少达到目标质量的方法；不是每张任务都重做研究。
- 调整路径：定位目标理解、事实、方法、工具用法或评价缺口，回到对应阶段；按 [research.md](research.md#能力与方法) 比较基线与新方法，必要时提出已授权范围内的小样实验。
- 协调写入：根据输入、契约与输出依赖确定受影响范围，暂停或收拢相关在途写入后更新方案；旧版本报告只作历史证据，不合入失效结论，继续真正无关的工作。
- 恢复条件：补齐决定性证据，重审变化的决策，更新消费者、就绪状态和检查；沿用有效授权，只确认变化的用户承诺，不以重规划降低验收或扩大范围。

# 实现与验证

- 工作区检查：先看实际文件，保留他人改动；按已批准增量实现，开发者自测仅作补充。
- 任务闭环：记录起始 revision 或产物状态，派发有界简报，收集报告与变更范围，独立审查、修复并仅复审受影响部分，再推进。
- 复审上限：到达循环上限时升级、更换所派身份或由主代理裁决，不搁置验收阻塞项。
- 失败诊断：没有新证据的重复失败须停止盲试，复现并缩小问题，一次验证一个假设；修复根因后重查回归与原场景，再决定升级或重设计。
- 独立检查：产物形成后使用新的独立验收作者，需求与规范使用不同审查上下文；用户可见阶段由另一名新身份检查，非交互阶段用真实 API、CLI 或集成检查。
- 基线保护：不得降低阈值、删除或跳过检查、加入空实现；不弱化验收标准或已批准基线。
- 证据更新：修复后在新构建上重查受影响部分；保留未受影响证据时，说明适用依据。
- 阻塞处理：阻塞验收的缺陷均在范围内，与来源无关；其他改进另列任务。
- 能力不足：继续未受影响工作，记录部分交付与下一步允许动作。
- 纯设计：结论止于已批准的设计深度，运行证据保持待完成。
- 完成条件：独立检查和集成通过、验收阻塞项关闭、记录已更新一致。
